# 知芽｜项目设计与开发规范（精简版 v1.1）

> **团队：** 妈妈夸我说的队  
> **版本：** v1.1（修订评审稿）｜**修订日期：** 2026-11-04  
> **修订来源：** v0.1（2026-11-03），本次根据系统设计说明书 v0.6、数据库设计说明书 v0.2 的交叉审核扩充命名规则；v1.1 需经团队确认后冻结。  
> **适用对象：** 前端、后端、领域智能体、知识工程、测试、部署与硬件成员  
> **依据：** GB/T 8567—2006《计算机软件文档编制规范》（重点参照系统/子系统设计、接口设计、软件设计、数据库设计相关章节）  
> **项目边界：** Web 软件与领域智能体为必做主体；ESP32-S3 墨水屏学习机为可选拓展。

本规范保留 **5 条核心规定**，其中第 3 条扩展为可执行的跨层命名与映射约定。目标不是增加文档数量，而是保证《系统设计说明书》《数据库设计说明书》与实际开发保持一致，并能在课程验收时逐项核对。

## 规定 1｜需求先行，所有设计可追溯

1. 以团队评审通过的《知芽软件需求规格说明书》作为唯一需求基线；当前 v0.2 是待评审版本，不应直接视为已冻结需求。
2. 每项核心功能均保留固定需求编号；系统设计写明所归属模块，数据库设计写明相关表，测试文档写明对应验收用例。
3. 新增或调整需求必须先记录 **修改原因、影响模块、负责人、日期和版本**，再同步更新设计图、接口和测试用例。
4. 优先保证软件独立上线、亲子共读、儿童自主阅读、原创短篇故事、受控分支和阅读反馈。**实时生成全套高质量插图、无限续写、完整实体学习机** 不作为默认必做项。

**追溯示例：** `FR-17 故事分支延续` → 故事分支模块 → 分支提交接口 → `story_branches` / `interaction_events` → `TC-FR17-01` 测试用例。

## 规定 2｜自顶向下分层设计，图文必须一致

设计说明书按同一顺序逐层展开，**每深入一层，增加可用于实现的细节**：

| 层级 | 应回答的问题 | 知芽示例 |
|---|---|---|
| L1 系统级 | 用户是谁、系统边界在哪里、如何部署？ | 家长 Web、FastAPI、模型 API、数据库、可选学习机 |
| L2 子系统级 | 各部分负责什么、依赖什么？ | 前端、业务后端、智能体、知识库、音频服务 |
| L3 模块级 | 模块怎样协作完成一项任务？ | 阅读会话 → 当前绘本上下文 → 提问策略 → 语音输出 |
| L4 详细设计级 | 具体输入输出、数据和失败处理是什么？ | 接口请求体、状态流转、表字段、超时及重试 |
| L5 验证级 | 怎样证明按设计实现？ | 单元/集成测试、智能体对比、上线验收 |

**统一用图规则：** 系统架构图描述组件与依赖；UML 用例图描述用户功能；活动图描述条件分支；顺序图描述调用先后；类图描述业务类关系；ER 图描述数据库实体、主外键和基数。图上的名称、箭头含义、关系类型须与正文一致；保留 `.puml`、`.mmd` 等可编辑源文件，不能只留截图。

**两份主文档的边界：**《系统设计说明书》重点写架构、模块、流程、接口、Agent 与部署；《数据库设计说明书》重点写概念模型、ER 图、表结构、字段字典、约束、索引和数据安全。两份文档应相互引用，不重复定义相互矛盾的字段。

## 规定 3｜统一命名、术语和缩写（全团队强制执行）

> **规则的地位：** 本节明确命名原则与**推荐统一方案**。两份已有设计文件存在冲突时，先在 PR 中确认本节“待冻结决策”，通过后再一起修改系统、数据库、图表和接口。不能单靠改变名称掩盖数据结构差异。

### 3.1 缩写、中文术语与图示

1. **每份正式文档首次出现缩写**按“中文名称（英文全称，缩写）”定义；后续统一使用缩写。文档开头维护缩写表，图上的缩写与正文一致。
2. 术语、接口对象、UML 类及数据库表应有唯一对应关系；不能用“绘本 ID”同时指绘本本体与特定版本。
3. 界面面向家长和幼儿用通俗中文，不直接展示 `RAG`、`ASR`、`LLM` 或底层枚举码。
4. `ESP32-S3`、`Vue`、`FastAPI`、`Git` 属于产品/技术名称，说明其作用即可，无需强行扩展英文全称。
5. UML 用例图、活动图、类图、时序图、协作图分别采用对应的标准记法；协作图在文中可说明为 UML 通信图（Communication Diagram）。

### 3.2 领域实体唯一命名（推荐统一方案）

以业务概念为准；**账号统一为 `Account`，家长是 `role=GUARDIAN`，不是另一张家长账号表**。绘本本体与绘本版本分别建模，并沿用数据库文档现有的版本化结构。下表需在团队评审后作为全项目术语基线。

| 中文业务名称 | UML / ORM 类名 | 对外 JSON 标识 | 数据库表名 | 说明 |
|---|---|---|---|---|
| 用户账号 | `Account` | `accountId` | `accounts` | 角色 `GUARDIAN`、`ADMIN`；不要并行使用 `guardian_users` |
| 登录凭证 | `AuthSession` | `authSessionId`（仅内部或必要时） | `auth_sessions` | 不对前端暴露明文令牌 |
| 幼儿阅读档案 | `ChildProfile` | `childProfileId` | `child_profiles` | `guardian_id` 关联 `accounts.id` |
| 绘本 | `Storybook` | `storybookId` | `storybooks` | 同一本绘本的稳定身份，不等于版本 |
| 绘本版本 | `StoryVersion` | `storyVersionId` | `story_versions` | 审核、修订、历史复读固定到版本 |
| 绘本页面 | `StoryPage` | `pageNumber` | `story_pages` | 由版本 ID + 页号共同定位 |
| 故事分支 | `StoryBranch` | `branchId` | `story_branches` | 分支起止页必须属于同一版本 |
| 阅读会话 | `ReadingSession` | `readingSessionId` | `reading_sessions` | 必须绑定档案及具体版本 |
| 互动事件 | `InteractionEvent` | `interactionEventId` | `interaction_events` | 标识事件与请求幂等键不可混同 |
| 阅读小结 | `ReadingReport` | `readingSessionId`（关联键） | `reading_reports` | 每个阅读会话至多一份 |
| 儿童授权 | `ChildGrant` | `childGrantId` | `child_grants` | 管理儿童模式有效期与访问范围 |
| 儿童可读版本 | `ChildGrantBook` | `childGrantId` + `storyVersionId` | `child_grant_books` | 授权与绘本版本多对多关联 |
| 知识版本 | `KnowledgeItem` | `knowledgeItemId` | `knowledge_items` | 保存可追溯的知识来源与版本 |
| 互动引用依据 | `EventEvidence` | `interactionEventId` + `knowledgeItemId` | `event_evidence` | 关联实际使用的知识依据 |
| 请求执行记录 | `RequestExecution` | `clientRequestId` | `request_executions`（待补表） | 幂等占位和模型调用状态 |

**固定中文术语：**“亲子共读模式”和“儿童自主阅读模式”不能混称；“原创故事文本”不等于“实时生成全套专属插图”；“受控分支”不等于“无限实时续写”；“阅读反馈”不等于“儿童能力诊断”。

### 3.3 跨层命名风格与文件规范

| 场景 | 统一规则 | 正确示例 / 例外 |
|---|---|---|
| Vue 组件 | `PascalCase.vue` | `StoryReader.vue`、`ChildModeSettings.vue` |
| Vue 组合式函数 | `use` + `PascalCase` | `useReadingSession.ts` |
| 前端 TypeScript / JavaScript 变量、函数、对象键 | `camelCase` | `currentPage`、`fetchStoryVersion()` |
| 前端类型 / 类 / 枚举类型 | `PascalCase` | `ReadingSessionDto`、`ReadingMode` |
| Python 模块 / 文件 / 函数 / 变量 | `snake_case` | `reading_service.py`、`create_session()` |
| Python 类名 | `PascalCase` | `ReadingSessionService`、`StoryVersion` |
| 数据库表 | 小写复数 `snake_case` | `reading_sessions`、`story_versions` |
| 数据库列 / 索引 / 约束 | 小写 `snake_case` | `version_id`；`idx_reading_sessions_profile_created` |
| 数据库主键 / 外键 | 主键 `id`（复合键例外），外键 `{关联对象}_id` | `reading_sessions.id`、`profile_id`、`version_id` |
| JSON 请求 / 响应字段 | `camelCase` | `storyVersionId`、`expectedRevision` |
| REST 路径 | `/api/v1/` + 小写复数资源 + `kebab-case` | `/api/v1/reading-sessions/{session_id}` |
| API 路径参数 | `snake_case`，与后端函数签名一致 | `{session_id}`、`{version_id}`；文档不混用 `{id}` 与 `{session_id}` 而不解释 |
| URL 查询参数 | 对外统一 `camelCase` | `pageSize`、`ageBand` |
| 常量 / 环境变量 | `UPPER_SNAKE_CASE` | `MAX_AUDIO_SECONDS`、`MODEL_API_KEY` |
| API 错误码 / 枚举值 | `UPPER_SNAKE_CASE` | `SESSION_CONFLICT`、`IN_PROGRESS` |
| Git 分支 | `feat/`、`fix/`、`docs/` + `kebab-case` | `docs/unify-db-schema` |
| Git 提交 | `类型(模块): 简要动作` | `docs(database): align session fields` |
| 技术文档与图源 | 英文 `kebab-case`，用语义后缀 | `reading-sequence.puml`、`api-contract.md` |
| **课程指定交付物** | **按课程要求中文文件名**；版本号只用于工作稿 | `妈妈夸我说的队_系统设计说明书.pdf`（最终交付） |
| 测试文件 / 用例 ID | `test_*.py` / `*.spec.ts`；ID 可追溯需求 | `test_reading_service.py`、`TC-FR17-01` |
| Markdown 章节/图片标题 | 中文明确主题、图号连贯 | `图 4-6 分支选择时序图` |

**异常处理：** 已存在技术框架固定名称或第三方字段时，只在适配层转换，不要求篡改外部协议；转换规则必须文档化。

### 3.4 主键、版本和页码的语义必须区分

| 语义 | API 字段 | 数据库字段 | 注意 |
|---|---|---|---|
| 绘本本体 | `storybookId` | `storybooks.id` / `story_versions.storybook_id` | 不代表特定图文版本 |
| 绘本版本 | `storyVersionId` | `story_versions.id` / `reading_sessions.version_id` | 读书、授权、分支固定版本 |
| 展示版本号 | `versionNumber` | `story_versions.version_no` | `versionNumber` 不是版本主键 |
| 绘本页面 | `pageNumber` | `story_pages.page_no` | 页面定位还需 `storyVersionId` |
| 会话进度页 | `currentPage` | `reading_sessions.current_page_no` | 避免与页面主键混用 |
| 乐观并发版本 | `revision` / `expectedRevision` | `reading_sessions.revision` | 不等于绘本版本号 |
| 事件去重标识 | `clientEventId` | `interaction_events.request_key`（候选） | 仅在会话范围内唯一；与事件 PK 不同 |
| 跨任务请求去重标识 | `clientRequestId` | `request_executions.client_request_id` | 需按作用域联合唯一 |
| 时间 | ISO 8601 UTC 文本（对外） | UTC 毫秒整数（当前数据库方案） | 由序列化层转换 |

**ID 类型待冻结：** 当前数据库采用 `INTEGER` 主键，但系统接口示例使用 `cp-demo`、`rs-demo` 等字符串 ID。建议首版**对外使用整数 ID**，改写样例并始终进行服务器端归属校验；如团队决定保留不透明字符串 ID，必须为需要对外暴露的对象统一增设 `public_id` 及唯一约束，明确内外 ID 映射。两种方案二选一，不能一处整数、一处字符串且没有映射。

### 3.5 枚举字典必须有唯一名称与语义

**建议以系统文档的阅读模式枚举为统一方向**，数据库相应更新；以下为拟统一字典，正式冻结前须确认业务含义。

| 字段/范围 | 候选统一值 | 与旧稿的冲突/处理 |
|---|---|---|
| `ReadingMode` | `PARENT_CHILD`、`CHILD_SOLO` | 替换数据库文档 `CO_READ`、`CHILD` |
| `ReadingSession.status` | `CREATED`、`IN_PROGRESS`、`FINISHED`、`INTERRUPTED` | 两份文档基本接近，统一状态转移和终态 |
| `ReadingSession.endReason` | `USER_FINISH`、`TIME_LIMIT`、`CONTINUED`，以及经评审确定的中断原因 | 续写标记为结束原因，不混作会话状态 |
| `InteractionEvent.eventType` | `STARTED`、`PAGE_CHANGED`、`QUESTION`、`ANSWER`、`ASK`、`FEEDBACK`、`BRANCH_CHOSEN` | `QUESTION`=系统引导提问；`ANSWER`=孩子作答；`ASK`=孩子主动提问；每种用法须由事件接口与数据字典一致定义 |
| `StoryVersion.status` | `DRAFT`、`PENDING_REVIEW`、`CHECK_FAILED`、`PUBLISHED`、`APPROVED_PRIVATE`、`RETIRED`、`WITHDRAWN` | 原数据库 `APPROVED` 建议改为 `APPROVED_PRIVATE`（私有原创）；公开发布与私有批准有别 |
| `RequestExecution.status` | `RUNNING`、`SUCCEEDED`、`FAILED`、`UNKNOWN` | 仅在决定纳入幂等执行表时要求存储；失败重放规则由系统文档定义 |
| `ReadingReport.status` | `PENDING`、`READY`、`FAILED` | 两份文档均保持这一口径 |

同一枚举值不得表达两个不同业务含义；字段取值必须写明**触发者、允许前置状态、结果状态、失败处理**。对内表示与对外展示文案通过映射表转换。

### 3.6 Agent、领域知识和接口命名

- Agent 的逻辑模块固定使用 `ReadingAgent`、`KnowledgeService`、`VoiceService`（如架构图已采用其他名字，先统一一次并备案），不要称一个外部大模型接口为独立的多个 Agent。
- 模型生成结果与数据库实体区分：`AgentResult` 是服务返回对象，不默认为业务表；知识引用采用 `KnowledgeItem`、`EventEvidence` 两类持久化对象。
- 外部接口 JSON 固定使用 `inputText`、`outputText`、`sources`、`readingSessionId`、`storyVersionId` 等经评审字段；源数据结构以正式 API 契约为准。
- 当出现 `reviewStatus`、`status`、`generationStatus` 等不同状态时，显式标明对象归属，不能因为都叫“状态”而混为一谈。
- 路径和请求体必须与“接口契约”一致；图中的消息名尽量直接沿用 API 路径和方法或服务方法名。

### 3.7 图、文档、分支和版本命名

1. 图源以 `图号-主题` 的稳定命名保存，例：`fig-4-06-branch-selection-sequence.puml`；导出图片同基名 `.svg` / `.png`，修改图源时同步更新导出图和图内文字。
2. 团队内部编辑稿建议 `system-design-v1.1.md`、`database-design-v1.1.md`；提交课程时仍使用指定中文文件名，不在正式文件名附加 `(最终版)(真的最终版)`。
3. 规范文件采用 `知芽_项目设计与开发规范_精简版_v1.1.md`；修改要求采用 `知芽_系统与数据库设计说明书_修改要求_v1.1.md`。
4. 设计稿版本号和数据库模式迁移号**分别管理**：`v1.1` 表示文档版本，不自动表示 schema 迁移版本或发布版本。
5. PR 标题示例：`docs(design): align story version and session schema`。PR 内写明涉及的 FR 编号、修改文档、图号、兼容性影响、测试或检查结论。

### 3.8 唯一来源、变更和审查

`docs/standards/glossary.md` 为公共术语、ID 语义与枚举字典的唯一来源；`docs/design/api-contract.md` 为接口字段及路径的唯一来源；《数据库设计说明书》为物理表字段和关系约束的唯一来源。《系统设计说明书》引用它们，保留流程所需的关键字段，但不维护另一套冲突的物理数据字典。

**变更步骤：** 提出术语/实体变更 → 在 PR 中记录动因与需求影响 → 由组长确认 → 更新词汇表、接口契约、数据库和 UML → 更新示例与测试 → 交叉审查合并。未冻结的候选方案请标注“待确认”，不得写成已完成实现。

## 规定 4｜前后端、数据库和智能体先定接口，再并行开发

1. **接口先约定：** 每个 API 写明请求方法、路径、身份权限、请求 JSON、响应 JSON、状态码、失败处理及负责人，形成一份可共享的接口契约。
2. **数据库先设计核心实体：** 先确定绘本、阅读档案、阅读会话、故事分支和互动事件等实体的主外键、约束、索引和迁移方式，再开发依赖它们的复杂业务。
3. **智能体流程可解释：** 记录输入（年龄、绘本页、回答）、知识来源、模型调用、规则约束、工具调用、结果校验与失败回退。不得把模型臆造的测试结果、引用或语音识别结果当成真实数据。
4. **软硬件职责分离：** Web 系统必须独立完成核心功能；ESP32-S3 仅通过后端受控接口获取绘本、上传按键或录音、接收音频，不在设备内保存模型 API 密钥。

**接口示例（设计草案）：** `POST /api/v1/reading-sessions/{session_id}/branches`；提交已允许的选项，后端校验会话和节点，返回下一段故事或明确的错误信息。具体字段以接口评审后的正式契约为准。

## 规定 5｜开发、测试与交付使用同一验收口径

1. **软件优先：** 优先打通“家长选绘本 → 阅读 → 智能提问 / 回答 → 受控调整 → 保存记录”的端到端流程，再补原创故事、语音和硬件拓展。
2. **完成标准统一：** 功能“已完成”必须同时有代码、可复现操作、异常处理和对应测试；原型、计划、模拟数据不得当作已实现功能。
3. **AI 必须对比验证：** 用相同底座模型与固定案例，比较通用问答和领域知识增强后的适龄性、情节一致性、引导合理性、安全性；保留原始输出和评价记录。
4. **儿童安全底线：** 家长控制儿童模式；默认最小化采集儿童信息和录音；识别错误可重试或选择按钮；不提供儿童能力诊断；限制不适龄内容和无限制聊天。
5. **Git 与文档同步：** `main` 保持稳定，使用功能分支和 PR；公共接口、数据库、核心规则变更必须同步更新设计图、数据字典、术语表及测试，不允许将密钥、真实儿童录音或敏感数据提交仓库。
